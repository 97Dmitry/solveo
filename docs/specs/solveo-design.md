# Solveo — проект приложения

Статус: проект для обсуждения; реализация не начата.

## 1. Назначение и согласованные решения

Solveo — Windows-приложение для помощи во время интервью. Основной путь:
подготовить контекст интервью, снять задание по хоткею, получить ответ,
продолжить разговор текстом или новыми снимками. Обычный чат без изображений
и без предварительной настройки также обязателен.

Пользователь согласовал:

- Название Solveo, приватный репозиторий `97Dmitry/solveo`.
- Go + Wails + React; frontend создаётся через Vite+ CLI (`vp`).
- Пакетный менеджер React/frontend — pnpm, единственный lockfile pnpm-lock.yaml.
- Полный перенос возможностей Screen Codex, с новым удобным интерфейсом чата.
- Две независимые функции: отдельная преднастройка чата и обычные сообщения.
- Существующий Screen Codex остаётся рабочим отдельным приложением.
- Проверку исключения из захвата на Windows выполняет пользователь.
- На данном этапе нужен письменный проект, без браузерного макета.
- Архитектура допускает разные LLM-подключения; сейчас реализуется только Codex.
- Будущие возможности включают получение вопроса из аудиозаписи интервью.
- Закрепление основного окна поверх остальных входит в первую версию.

Ниже конкретные решения являются предложениями исполнителя до утверждения
документа. Код пока не генерировать. Коммиты и push отдельно не разрешены.

## 2. Границы первой версии

Первая версия сохраняет существующий backend Codex CLI за общим контрактом
LLM-подключения. Claude Code и локальные модели предусмотрены архитектурой,
но их адаптеры пока не реализуются. Универсальность текущей версии
означает поддержку разных вопросов при одном работающем подключении.
Основные сценарии: задачи с кодом, теория и архитектура; свободный вопрос
доступен без выбора категории. Категории не становятся обязательными режимами.

В текущую реализацию не включать распознавание речи, запись аудио интервью, автономное управление
компьютером, облачную синхронизацию, аккаунты, платежи, библиотеку шаблонов,
новые провайдеры или автоматическое чтение всего экрана. Снимки делаются
только по действию пользователя. Новые возможности не должны вытеснять
полноту переноса уже существующих.

Будущие подключения и аудио описаны в §9.1 и §9.2. Не добавлять сейчас
неработающие пункты выбора, плагины, speech dependencies или фоновые записи.

## 3. Преднастройка чата

Это самостоятельная панель «Настройка чата», а не сообщение в переписке.
Доступна при создании разговора и после его начала. Настройка необязательна.
Предлагаемый состав:

| Поле | Назначение | Значение без настройки |
|---|---|---|
| Название | Найти интервью в истории | Автоматическое по первому вопросу |
| Контекст интервью | Позиция, стек, уровень, описание будущих заданий | Пусто |
| Требования к ответам | Акценты, ограничения, желательный формат | Пусто |
| Язык ответа | Язык объяснений | Русский |
| Язык кода | Предпочтительный язык для задач с кодом | Автоматически по заданию |
| Подробность | Кратко или подробно | Кратко |
| Подключение LLM | Сейчас только Codex; выбор расширится с адаптерами | Codex |
| Модель и параметры | Настройки, поддержанные выбранным подключением | Значения подключения по умолчанию |

Контекст и требования — многострочные свободные поля; они допускают
произвольный текст, а не только выбор из списка стеков. Позиция и стек
пока не выделяются в отдельные обязательные сущности.

«Сохранить» сохраняет настройку локально, не запускает Codex и не создаёт
сообщение модели. «Отмена» закрывает панель без применения изменений.
Чат с сохранённой настройкой виден в истории даже до первого запроса.

Редактировать можно в idle-состоянии. После начала переписки новые настройки
действуют со следующего запроса, не переписывают предыдущие ответы и не
создают новый разговор. У запроса сохраняется версия применённой настройки.
Старый контекст может остаться в серверной сессии подключения; полное удаление его влияния требует
нового чата. UI объясняет это рядом с сохранением изменений активного чата.
Смену модели применять к следующему запросу; отказ CLI показать явно.

## 4. Сообщения и вложения

Один composer поддерживает три варианта: текст, изображения, текст с
изображениями. Ни одного вложения для старта не требуется. Пустое сообщение
без вложений не отправляется. Текст и преднастройка никогда не смешиваются
в одном поле ввода.

Первый запрос начинает разговор выбранного подключения. Codex создаёт
CLI-сессию; последующие запросы продолжают именно её. Другие будущие
адаптеры могут получать историю явно, без внешней сессии.
Новые снимки не создают новый чат автоматически. «Новый чат» создаёт
отдельный разговор с пустой преднастройкой; текущая история сохраняется.
Ошибка продолжения не должна незаметно начинать новую внешнюю сессию.

Текст плюс снимки отправляются одним ходом, PNG — в порядке очереди.
Для снимка без текста использовать нейтральный запрос: помочь с заданием
на изображении с учётом настройки чата. Если снимок содержит несколько
неоднозначных вопросов, модель должна уточнить, а не придумывать цель.

В переписке видны пользовательский текст, вложения и ответ. Вложение связано
с конкретным пользовательским сообщением. У кода — подсветка и копирование;
у ответа — копирование текста. Сохраняется действие копирования последнего
блока кода, увеличение/уменьшение текста и список всех фото разговора.

Ответ по умолчанию краткий и ориентирован на задачу. Для кода: рабочее
решение, затем краткое объяснение и сложность, когда это уместно. Для
теории: прямой ответ и основные аргументы. Пользовательская настройка
формата имеет приоритет над этими общими рекомендациями. Не навязывать
код любому вопросу и не выдумывать опыт кандидата при вопросах об опыте.

## 5. Захват, очередь и хоткеи

Сохранить основной монитор и выбор области. Мульти-мониторный захват
не добавляется в эту версию. Предлагаемые действия:

| Действие | Хоткей | Поведение |
|---|---|---|
| Снимок и ответ | Ctrl+Alt+S | Выбрать область и сразу отправить новый снимок |
| Добавить снимок | Ctrl+Alt+A | Выбрать область и добавить в composer |
| Снимок монитора | Ctrl+Alt+F | Снять основной монитор и сразу отправить |
| Отправить подготовленное | Ctrl+Alt+Enter | Отправить текст и очередь composer |
| Показать/скрыть | Ctrl+Alt+O | Переключить главное окно |

Быстрый снимок отправляет только новый снимок, не отправляя без спроса
ранее набранный текст и другие вложения. Они остаются в composer. Все пути
работают с выбранным чатом и его сохранённой преднастройкой. Выделение
отменяется Esc или правой кнопкой, снимок делается отпусканием левой.

Лимит очереди 20. До быстрого capture резервируется место на случай ошибки;
при заполненной очереди захват отклоняется до выбора области. Успешная
отправка удаляет только реально отправленные вложения. Неудача быстрого
запроса добавляет его снимок в очередь текущего чата для явного повтора.

Черновик текста и очередь принадлежат чату, а не всем разговорам сразу.
Переключение истории не переносит вложения в чужой разговор. В пределах
запуска черновики хранятся для своих чатов; неотправленные PNG временные
и удаляются при штатном выходе, как в прежнем приложении. Преднастройка
и завершённая переписка сохраняются между запусками. Постоянное хранение
неотправленных черновиков не входит в первую версию.

Во время запроса или выделения новые capture/request/check не запускаются.
Переключение чата, применение настройки и редактирование отправляемых
вложений блокируются. Можно читать чат, копировать текст, менять тему,
смотреть фото, открывать лог и скрывать окно.

## 6. Главное окно

Верхняя строка: название разговора, новый чат, история, снимок и настройки.
Центральная область: переписка на доступную ширину. Снизу: миниатюры очереди,
многострочный ввод, добавить снимок, отправить/отменить и короткий статус.

В верхней строке отдельная toggle-кнопка «Закрепить поверх окон» с видимым
активным состоянием; то же действие доступно из трея. По умолчанию выключено,
выбор сохраняется как общая настройка, не как параметр чата. Можно переключать
во время запроса. Использовать Wails WindowSetAlwaysOnTop; при старте применять
сохранённое значение до первого показа. При скрытии окно остаётся скрытым,
закрепление не вызывает show/focus; при повторном открытии режим сохраняется.
Переключение не влияет на capture affinity. Основное окно не должно перекрывать
region selector или принадлежащий приложению просмотрщик/диалог; их порядок
показа и owner/topmost поведение обрабатывает Windows-слой. За пределами обычных
окон рабочего стола не обещать приоритет над secure desktop или exclusive fullscreen.

История открывается боковой панелью. Настройка чата, общие настройки,
история и фото не конкурируют за ширину одновременно: открыта одна панель.
На минимальной ширине панель занимает место области чата, а не сжимает
сообщения до узкой колонки. Минимальная клиентская область — 520x400.

Предлагаемый стиль: спокойная светлая и тёмная темы, ясная типографика,
один акцентный цвет, аккуратные границы вместо обилия карточек. Ответам
отдать больше места, чем декоративным элементам. Длинный код прокручивается
горизонтально внутри блока, а не растягивает окно. Текст сообщений выделяется
обычным браузерным способом. При чтении старого ответа приход нового не
сбрасывает позицию; появляется действие перехода к последнему сообщению.

Enter отправляет, Shift+Enter добавляет строку; IME composition не запускает
отправку. Во время запроса кнопка становится «Отмена». Автофокус не должен
мешать работе в другом приложении. Приход ответа, лога или ошибки не показывает
скрытое окно, не выдаёт toast и не перехватывает фокус. Статус доступен после
явного открытия. Ошибки старта и отказ восстановления трея — отдельные случаи,
где требуется доступный пользователю путь выхода.

В общих настройках: тема, размер текста, информация о хоткеях и доступ к
проверке соединения и логу. Не добавлять редактор произвольных shell-команд.
UI на русском, идентификаторы и технические сообщения сохраняют исходный язык.

## 7. Окна и Windows lifecycle

Рекомендована стабильная Wails v2; React/TypeScript работает в WebView2
главного окна. Не использовать Wails v3 beta для обхода ограничений v2.

Главное окно принадлежит Wails. Для Win32-служб — отдельный нативный host
на закреплённом OS-потоке с очередью сообщений: трей, хоткеи, выбор области,
нативное окно лога и просмотрщик изображений. Их общий theme path сохранить.
Прежний главный Win32 интерфейс с RichEdit и контролами не запускать.
Общение с host — сообщениями/командами, без прямых вызовов его окон из workers.
Вызовы Wails выполняются через его runtime и lifecycle, не через чужой WndProc.

Лог остаётся отдельным окном без taskbar entry, доступным из трея при скрытом
главном окне; содержит ограниченный буфер и отмену. Просмотрщик: fit, 1:1,
zoom колесом/кнопками, панорамирование, смена снимков, Esc. Закрытие этих окон
не завершает приложение. Внешний вид вспомогательных окон согласовать с темой
основного; переписывание их на React не является целью первой версии.

Старт: mutex архива → открытие хранилища → native host/tray/hotkeys →
скрытое окно Wails/WebView → защита главного окна → frontend-ready → показ.
Каждое top-level окно получает `WDA_EXCLUDEFROMCAPTURE` до первого показа.
Wails запускается со StartHidden и ContentProtection. Защиту подтвердить
Win32-вызовом до показа, не считать наличие флага проверкой результата.
Для поиска главного HWND использовать уникальный WindowClassName и PID
текущего процесса, а не заголовок окна. Не подменять WndProc Wails и не
обращаться к его приватным структурам. Точный lifecycle adapter проверить
первым техническим этапом до полного переноса UI.

Крестик скрывает главное окно; трей/хоткей возвращают. Выход — из трея
и через доступное действие приложения. После перезапуска Explorer восстановить
значок. Если это не удалось, дать явный путь выхода и восстановления видимости.
Если защита или регистрация трея на старте не удалась, главное окно не показывать,
сообщить ошибку и завершиться с освобождением ресурсов.

Реальный capture в Zoom и других программах проверяет пользователь.
Исполнитель обеспечивает соответствующие вызовы, порядок старта и сборку;
результат пользовательского runtime-теста фиксируется отдельно.

## 8. Go и React: границы состояния

Go владеет чатами, настройкой, очередями, черновиками разговоров, операцией,
логом, файлами и сохранением. React владеет открытой панелью, прокруткой,
состоянием редактора и несохранённой формой настройки. Изменения текста
передаются в Go с chat ID и возрастающей draft revision; устаревший callback
не перезаписывает новый текст. Переключение чата сначала подтверждает передачу
последнего текста, затем меняет выбранный чат. Доступность действий вычисляется Go; любой метод повторно
проверяет её независимо от disabled-кнопок frontend.

Отправка кнопкой или Enter передаёт актуальный текст явно и атомарно фиксирует
его вместе с выбранными вложениями. Native Ctrl+Alt+Enter создаёт намерение
отправки с уникальным ID: React получает его, завершает передачу актуального
текста и вызывает тот же submit. Во время IME composition отправка отклоняется.
При отсутствии подтверждения frontend запрос не запускается; нельзя отправлять
последний закешированный текст как запасной вариант. Намерение имеет timeout,
chat ID и draft revision; после смены чата, reload или timeout оно недействительно.
Go повторно проверяет состояние и принимает каждый submit ID не более одного
раза. Точный формат DTO оставлен исполнителю.

Небольшие пакеты:

- `internal/chat`: сообщения, конфигурация и её ревизии, вложения и состояния.
- `internal/app`: координация запросов, очередь, команды UI и готовые UI-снимки.
- `internal/llm`: минимальный контракт подключения и его возможности.
- `internal/llm/codex`: единственный реализуемый адаптер на основе прежнего CLI-клиента.
- `internal/history`: архив и чтение прежнего формата.
- `internal/capture`, `internal/instance`: адаптация существующей реализации.
- `internal/platform/windows`: host, трей, хоткеи и вспомогательные окна.
- `frontend/src`: app, chat, history, settings, viewer entry points и UI-компоненты.

Не вводить DI framework, event bus, transport-independent repository hierarchy
или обязательный frontend state manager. Начать с React state/context и одного
модуля Wails bridge. Wails генерирует bindings и TS-модели, не дублировать DTO
вручную. Команды Go имеют узкие типизированные аргументы и возвращают понятный
результат; не принимать произвольные file paths, JS или команды оболочки.

После подписки на события frontend получает snapshot с монотонной revision;
события до/после handshake не должны теряться или откатывать состояние.
Worker completion связан с operation ID, chat ID и revision настройки,
а не с текущим выбранным React-чатом. Повторная доставка одного результата
не добавляет второй ответ. Перезагрузка UI не повторяет отправку.

Изображения выдаются через локальный обработчик Wails по разрешённым attachment
ID. Бинарный PNG не включать в каждый snapshot; размер/метаданные отдельно.
Лог передавать ограниченными порциями, не пересылать весь буфер на каждую строку.

## 9. Codex и обработка запросов

Сохранить нынешний Codex CLI и его авторизацию. Переработать узкий клиентский
контракт под text + optional images как при старте, так и при resume.
До реализации сверить CLI-аргументы установленной версии. Не эмулировать
продолжение новой сессией при ошибке resume. Параметры модели и reasoning
остаются отдельными OS-аргументами.

Запрос формируется из общих инструкций, актуальной преднастройки и конкретного
сообщения; снимки — отдельными image-аргументами. При каждом ходе явно передать
актуальный блок преднастройки с его ревизией: сохранённая CLI-сессия не гарантирует
замену старых инструкций. Не называть этот блок system-role без поддержки API.
Локальная переписка показывает пользовательский текст без служебного блока;
применённая ревизия хранится в метаданных запроса.

Режимы: idle → selecting → capturing → requesting → saving → idle;
для текста начать с requesting, для check — отдельная операция без изменения
чата. В ходе request доступна отмена. После успешного ответа saving является
отдельной фазой; отмена больше не отбрасывает уже полученный ответ.
События прогресса показывают этап, ответ отображается после получения финального
текста. Настоящий token streaming не обещается и не требуется в первой версии.

Сохраняются timeout, временный рабочий каталог, `--sandbox read-only`,
`--ignore-user-config`, отсутствие transient console и отмена дерева
`codex.cmd` через `taskkill /T`. Проверка соединения — реальный запрос
без снимков, с выбранными model/reasoning и timeout в одну минуту.

Ошибка или отмена не удаляет сообщение, черновик и исходные снимки.
Не выполнять автоматический повтор: CLI-сессия могла уже принять ход.
Показать failed/canceled status и явный повтор; предупредить, если судьба
предыдущего хода неизвестна. Новый явный повтор — новая попытка, связанная
с прежним локальным сообщением, не дублирование сообщения в UI.

### 9.1. Независимость от конкретного LLM

В модели чата не должно быть обязательных Codex thread IDs, CLI-флагов или
общего набора параметров, который обязан поддержать каждый будущий движок.
Codex CLI, Claude Code и локальный HTTP runtime — разные адаптеры.
Qwen и Llama — семейства моделей; способ запуска локальных моделей выбирается
отдельно при реализации адаптера, например через Ollama или llama.cpp.
В текущей работе не выбирать и не запускать локальный runtime автоматически.

Минимальная граница: Generate(ctx, request, emit) → result/error, Check и
описание capabilities. Request содержит общую преднастройку, завершённую
историю, текущий ход с текстом/вложениями, выбранную модель и optional
continuation state этого подключения. Result содержит ответ и обновлённый
continuation state. ctx отвечает за отмену; emit — за прогресс и, если
подключение это поддерживает, будущие текстовые deltas. Для Codex первая
версия по-прежнему показывает финальный ответ, не имитируя token streaming.

История всегда доступна адаптеру: stateless-подключение сериализует её целиком
в пределах своих лимитов, stateful-подключение продолжает внешнюю сессию
и отправляет текущий ход. Не отправлять историю повторно в активную Codex-сессию.
При невозможности продолжить сессию не включать неявный fallback. Контракт
не навязывает HTTP, subprocess или наличие server-side sessions.

Capabilities определяют поддержку изображений, streaming и доступные параметры
генерации. Frontend получает их из Go: unsupported reasoning скрывается,
изображения для text-only модели не отправляются и не отбрасываются молча.
Существование локальной модели само по себе не означает поддержку снимков.
Параметры валидируются адаптером, без untyped map произвольных CLI-аргументов.
Конкретные дополнительные параметры вводятся вместе с реальным адаптером.

provider ID хранится в чате, model ID и параметры — в конфигурации/метаданных
попытки. После первого запроса смена подключения требует нового чата; чужой
continuation state не переносится. Можно заранее сохранить ту же преднастройку
для нового разговора, без автоматической отправки всей старой истории.
Сейчас UI показывает только рабочий Codex. Достаточно статической регистрации
одного адаптера; plugin SDK, динамический registry и другие реализации не нужны.

### 9.2. Будущий аудиоввод

Предусмотреть независимый путь: источник аудио → распознавание речи →
черновик текста → обычный механизм отправки чата → LLM. Распознавание речи
не является методом LLM-адаптера. Приложение должно уметь добавлять текстовый
черновик из другого источника через обычную app-команду, не обращаясь к DOM.
В future message metadata может появиться источник transcript; его отсутствие
в старых сообщениях нормально. Сейчас пустые speech interfaces не создавать.

Запись, транскрибация, raw audio storage и автоматическая отправка после
распознавания пока не реализуются. При начале этой функции отдельно определить:
микрофон или системный звук, ручной start/stop или иной режим, границы вопроса,
редактирование/подтверждение текста, хранение аудио и выбранный STT backend.
Не предполагать, что микрофон надёжно записывает звук собеседника из наушников.
Будущая audio pipeline не должна занимать CLI-process slot во время записи;
готовый текст подчиняется общим правилам отправки и привязки к чату.

## 10. Хранилище и идентичность

`solveo-data` рядом с EXE, независимо от cwd. Отдельный локальный chat UUID
создаётся до первого запроса; provider ID и optional provider continuation
state хранятся отдельно. Для Codex continuation state содержит session ID.
Поэтому преднастроенный, но ещё не отправленный чат можно архивировать.
Не использовать внешний thread ID в качестве единственного ID нового чата.

Предлагаемая schema v2: chat ID, provider ID, optional provider state, title, timestamps,
chat config/revision, messages и attachments. У сообщения: собственный ID,
role/text, attachment IDs, config revision и attempt/status metadata.
У attachment: ID, относительный PNG path и сведения для отображения.
Не хранить живые process handles или абсолютные временные пути в JSON.

Читать schema v1 Screen Codex без изменения оригиналов: старый thread ID
становится session ID адаптера Codex и локальным chat ID, provider ID = codex;
сообщения импортируются по
порядку, прежние снимки доступны на уровне чата. Не выдумывать отсутствующую
привязку старых изображений к сообщениям. Следующее сохранение — schema v2
с атомарной заменой документа. Для переноса пользователь копирует старый архив
в `solveo-data` при закрытых приложениях. Автомиграция исходной папки не нужна.

До сетевого запроса сохранить принятый пользовательский ход и его вложения;
если это не удалось, запрос не начинать, исходники оставить. После получения
ответа сначала архивировать его, затем удалять временные отправленные PNG.
Лимит JSON 32 МиБ, относительные пути и валидация сохраняются. Недописанный
request после аварийного запуска помечается interrupted, не отправляется сам.

При ошибке сохранения принятого ответа держать его и источники в памяти,
заблокировать новые запросы и смену чата до повторного сохранения либо явного
отказа. Повтор записи доступен отдельно и перед выходом. «Продолжить без
сохранения» явно отбрасывает только несохранённый результат, сохраняет старый
архив и необходимые снимки для дальнейшего выбора. Не продолжать слепо прежнюю
CLI-сессию после отказа от локального результата: начать новый локальный чат.
Это развитие прежнего действия «Новый без сохранения», без потери пути выхода.

Mutex фактического archive directory удерживается весь lifecycle.
При выходе отменить worker, дождаться освобождения ресурсов, завершить
native host, удалить безопасно удаляемые temporary PNG и закрыть mutex.
WebView profile — LocalAppData, отдельно от переносимого архива.
Общие настройки окна (в том числе always-on-top) хранятся отдельным
атомарно заменяемым документом settings.json в solveo-data, не внутри чатов.
Provider state не содержит токены/пароли; авторизация находится в CLI-профиле
или отдельном механизме credentials соответствующего будущего адаптера.

## 11. Frontend toolchain и ресурсы

Создать `frontend/` через `vp create` с React + TypeScript. Перед генерацией
проверить флаги установленного `vp`; локально ранее обнаружен CLI v1.3.0.
Согласованный package manager — pnpm под управлением Vite+, один pnpm-lock.yaml.
Использовать Vite+ для dev/build/check, без параллельного ESLint/Prettier.
Версии Go/Wails/frontend фиксируются при реализации после проверки совместимости.

В `wails.json`: frontend install/build/dev watcher вызывают `vp`, dev server
работает только для разработки. Production использует embedded `frontend/dist`.
Node.js, vp и dev server конечному пользователю не нужны. WebView2 Runtime
требуется; при отсутствии понятная ошибка, без автоматической установки.

Markdown без raw HTML; remote images и произвольные subresources запрещены.
Внешние ссылки не открывать в документе с Go bindings. Не загружать UI/CDN-шрифты
из сети. PNG endpoint не раздаёт локальную файловую систему. Релиз без devtools
и расширенных frontend capabilities. Логи ограничены и не получают полный
скрытый prompt, содержимое снимков и токены авторизации.

README: prerequisites, build/use, privacy и реальные ограничения. Bare make
показывает help. Разделить проверки frontend, обычные Go tests и Windows vet/build.
Не вводить Linux GUI dependencies в путь Windows cross-build без необходимости.

## 12. Этапы реализации и проверка

1. Windows lifecycle: скрытый Wails window, capture affinity, native host,
   hotkeys/tray, region selector и корректное завершение. При несовместимости
   API v2 сообщить конкретный blocker до полного переноса.
2. Модель чата и schema v2: независимые chat/session IDs, конфигурация,
   text/image turns, совместимость старого архива, recovery.
3. Контракт LLM и единственный адаптер Codex: start/resume для текста и снимков,
   capabilities, отмена и привязка результатов.
4. React chat, composer, настройка, история, темы и просмотр изображений.
5. Полнота вспомогательных окон, shortcuts, закрепление поверх окон, лог,
   connection check, проверки.

Ключевые сценарии приёмки:

- Сохранить преднастройку без вызова CLI; закрыть/открыть приложение и найти её.
- Начать без изображений; начать со снимка; отправить текст плюс несколько PNG.
- Продолжить тот же чат новыми снимками и текстом; новый чат имеет новый контекст.
- Изменить настройку после ответа, следующий запрос использует новую ревизию.
- Проверить порядок PNG, лимит очереди, ошибку быстрого запроса и явный retry.
- Сменить чат с черновиком и вернуться без попадания вложений в другой чат.
- Проверить отмену, timeout, запоздалый worker и отсутствие двойного ответа.
- Проверить архивный сбой до запроса и после ответа, повтор записи и recovery.
- Читать старую историю без ложных связей сообщений и фотографий.
- Проверить UI build/typecheck, Go tests, Windows vet/build и diff checks.
- Проверить always-on-top: переключение из UI/трея, сохранение между запусками,
  hide/show, отсутствие перехвата фокуса и доступность selector/viewer.
- Проверить, что чат и UI не требуют Codex-specific ID, а capabilities
  валидируют возможности реального Codex-адаптера. Другие адаптеры не писать.

Тесты нужны для правил состояния, prompt composition, архива, retry/отмены
и доставки результата. Не добавлять зеркальные тесты CSS или тривиальных setters.
Исполнитель проверяет сборку и доступные ему сценарии; пользователь проверяет
реальные Windows capture/Zoom и даёт результат. Непроверенные runtime-сценарии
обозначаются отдельно, не блокируют само проектирование.
