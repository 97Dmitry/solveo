Документ фиксирует продуктовые решения и критерии готовности; перед реализацией

## Цель и существующая основа

Цель — помощник для интервью, который автоматически выбирает способ обработки
вопроса, быстро выдаёт полезный ответ и сохраняет работу при сбоях. Пользователь
не должен вручную выбирать категорию задания или исправлять ошибки приложения.
Безошибочность ответов LLM не обещается; качество и задержка проверяются на
типичных вопросах до включения нового способа обработки по умолчанию.

Уже реализованы текстовый чат и вопросы со снимками, отдельная преднастройка,
очередь до 20 снимков, история, Codex-адаптер, выбор модели и reasoning,
просмотр снимков, трей и горячие клавиши, закрепление окна, тема и масштаб.
Есть сохранение результатов с восстановлением после ошибки записи, проверки
фронтенда и Go, линтер, нативные Windows-тесты и сборка Windows EXE в CI.
Повторная проверка прежних исправлений Claude отдельным этапом не требуется.

## Общие ограничения

- Сохраняем Go 1.27+, Wails и React/TypeScript; frontend — Vite+ и pnpm.
- Go владеет состоянием. События Wails проверяются Zod; DTO генерируются из Go.
- Данные остаются в `solveo-data` рядом с EXE; используем атомарную запись,
  проверяем пути и сохраняем совместимость существующих архивов и настроек.
- Время в Go и хранилище — UTC; локальное представление делает frontend.
- Основные запросы сериализуются, отправленное задание и его версия фиксируются.
  Отмена, повтор и поздние события привязаны к конкретной попытке.
- Неизвестный исход основного LLM-запроса не вызывает автоматическую отправку
  заново. Сохраняем состояние подключения и явно показываем неопределённость.
- Прогресс CLI и внутренние рассуждения не становятся основным ответом чата.
- Готовые UI-компоненты и библиотеки используем там, где они оправданы;
  зависимости выбираем по актуальной поддержке, распространённости и размеру.
- Тесты используют подмены подключений. Настоящие LLM-запросы нужны только для
  отдельно запускаемых измерений. Windows UI проверяется на Windows.

## 1. Параллельные подход и решение — эксперимент

**Приоритет:** получить краткий полезный подход раньше полного решения.
Вместо скрытого классификатора проверяем два независимых запроса Codex по
одному вопросу и снимкам: быстрый даёт суть и подход в 2–4 фразах без кода,
основной — свой подход, решение и короткое пояснение. Для теории код не нужен.

Эксперимент реализуется в ветке `feat/parallel-answers`; до проверки реальной
скорости и качества он включается явно в преднастройке чата. У основного и
быстрого запроса свои модель и reasoning из каталога Codex; пустые значения
означают настройки подключения, а не гарантированно быструю модель.

- [ ] **Первая проверка на Windows:** сравнить один запрос и два одновременных
  на одинаковых задачах. Замерить время от действия пользователя до полезного
  подхода, время полного решения и влияние конкуренции. В интерфейсе отдельно
  отображается длительность выполнения каждого запроса Codex, без сохранения.
  Настоящие запросы не входят в CI; измерения пользователь выполняет отдельно.
- [ ] На теории, коде, расчётах, архитектуре и неоднозначных снимках проверить
  корректность, достаточность контекста и расхождения подхода/решения.
- [x] Основной запрос продолжает точную сессию чата. Быстрый стартует отдельную
  сессию с преднастройкой, краткой историей без прежних быстрых догадок и снимками.
  Для текстового уточнения ему повторно передаются последние снимки задания;
  длинный текстовый контекст ограничен и помечен как сокращённый.
- [x] Один пользовательский ход содержит два блока с независимыми статусами,
  ошибками и длительностью. Подход отмечен предварительным; основной ответ
  должен самостоятельно проверить условия и назвать свой подход. Совпадение
  алгоритмов не гарантируется, автоматическая сверка не реализована.
- [x] Вход, снимки и параметры фиксируются до запросов. Подход сохраняется до
  завершения основного; состояние быстрого запроса не попадает в сессию чата.
- [x] Отмена останавливает оба запроса. Готовое решение отменяет оставшийся
  медленный подход, поздний предварительный текст не появляется задним числом.
- [x] Повтор запускает только основной запрос с исходными параметрами; успешный
  подход остаётся. Неизвестный исход не вызывает автоматическую отправку.
- [x] При сбое записи оба запроса отменяются, результаты и состояние основного
  собираются перед recovery. Повтор сохранения не вызывает LLM.

**Известное ограничение транспорта:** `codex exec --json` передаёт текст
`agent_message` целиком в `item.completed`, без текстовых частей. Для этого
эксперимента поток не требуется: каждый блок показывается после своего запроса.
Два запроса расходуют больше лимита; выигрыш скорости пока не подтверждён.

**Отдельное последующее улучшение — текстовый поток:** app-server поддерживает
`item/agentMessage/delta`, но не `--ignore-user-config` (справка Codex 0.163.0).
Прототип на Windows подтвердил изоляцию отдельным `CODEX_HOME` с отключёнными
плагинами и skills, продолжение сессии и отмену
([замеры](2026-10-21-codex-latency.md#изолированный-app-server-прототип)).
Потоковый транспорт реализован ([план](../superpowers/plans/2026-10-21-appserver-streaming.md)),
проверен на Windows и измерен: быстрее exec примерно вдвое на новом чате и в
~9 раз на уточнении. По решению пользователя (2026-10-21) он единственный:
`codex exec` и состояние прежних чатов удалены, такие чаты доступны только для
чтения. Параллельный режим оставлен для будущих локальных моделей. Порядок
«суть → подход → код» внутри одного ответа не сокращает ожидание этого ответа.
Протоколы: [exec JSONL](https://developers.openai.com/codex/noninteractive/),
[app-server deltas](https://developers.openai.com/codex/app-server/).

**Критерий готовности эксперимента:** пройдены автоматические проверки
конкурентности, сохранения, отмены и повтора; собран Windows EXE. Для включения
по умолчанию дополнительно нужны реальные измерения задержки и качества.
Численные цели и приемлемую частоту расхождений устанавливаем после замеров;
мгновенный правильный ответ не обещаем. Технические детали и проверки — в
[плане реализации](../superpowers/plans/2026-10-21-parallel-answers.md).

**Модули:** `internal/chat`, `internal/llm`, `internal/llm/codex`,
`internal/app`, `internal/history`, frontend bridge/chat/settings.

**Критерий готовности:** история быстро находится, длинный чат не мешает вводу,
конфликты хоткеев объясняются, настройки переживают перезапуск. Миграции настроек
сохраняют текущие значения темы, масштаба, шрифта и закрепления окна.

**Модули:** `internal/history`, `internal/settings`, `internal/platform/windows`,
`frontend/src/history`, `frontend/src/chat`, `frontend/src/settings`.

## 7. Подготовка к рабочему использованию

- [ ] Объединить существующую проверку подключения с проверкой записи данных,
  регистрации хоткеев, выбранных параметров и незавершённых сохранений.
- [ ] Показывать время последней успешной проверки. Проверку с запросом модели
  запускать явно; она не должна изменять активный разговор.
- [ ] Проверить на Windows полный путь: подготовка → вопросы и снимки → отмена →
  обрыв связи → восстановление → перезапуск. Включить длинные ответы,
  заполненную очередь и недоступность диска.

**Критерий готовности:** есть понятные пути восстановления основных сбоев;
актуальные проверки CI и ручная Windows-приёмка пройдены. Сборка сама по себе
не подтверждает UI, фокус, захват, трей и поведение хоткеев.

Ближайший выпуск охватывает этапы **1–7**, включая 2.1 и 2.2. Каждый этап завершается собственными
проверками; общий сценарий этапа 7 не заменяет проверку каждого изменения.

## 8. Дополнительные LLM-подключения

После стабилизации основных функций добавить второй адаптер через существующий
`llm.Provider`: Claude Code либо локальное подключение. Конкретный вариант
выбрать под нужный сценарий перед реализацией.

- [ ] Реальный выбор подключения и учёт поддержки снимков, параметров и частей ответа.
- [ ] Новое подключение начинает новый чат; состояние Codex ему не передаётся.
- [ ] Не добавлять неработающие пункты выбора или динамическую систему плагинов.

**Критерий готовности:** оба адаптера проходят общие контрактные и сбойные
сценарии; неподдерживаемые возможности явно обозначены.

## 9. Аудио — отдельный поздний этап

Проект подробного плана для обсуждения: [локальное аудио и смешанная RU/EN речь](../superpowers/plans/2026-10-22-local-audio.md).
Первым реализуется Qwen3-ASR-1.7B без квантования через `stt.Provider`,
с локальным streaming на vLLM в Docker и контекстным IT-словарём.
Качество и работа двух источников проверяются на целевом ПК до включения.
Отсев 2026-10-23: выбран hybrid final, порог по терминам ≥80%;
Nemotron проверен и отклонён для смешанной RU/EN речи.

После основных функций: системный звук и микрофон → распознавание речи →
редактируемая карточка вопроса → подтверждение → существующая отправка.

- [ ] Отдельные модули захвата аудио и STT с одним проверенным распознавателем.
- [ ] Прослушивание независимо от единственного слота LLM-операций; ограниченные
  буферы, видимые сбои устройств и привязка фрагментов к исходному чату.
- [ ] Предварительная/подтверждённая расшифровка с источником, временем и версией;
  исходное аудио по умолчанию только во временном ограниченном буфере.
- [ ] Карточка вопроса не перезаписывает обычный черновик. Новая речь не меняет
  уже отправленную версию; повторное действие не создаёт дубликат запроса.
- [ ] Управление контекстом без повторной отправки всей расшифровки в активную
  Codex-сессию. Сохранять связь вопроса с исходными репликами.
- [ ] Испытания на записях с паузами, перебиваниями и техническими терминами.
  Затем автоматическое предложение карточек; автоматическая отправка —
  отдельное решение по измеренной частоте ложных срабатываний.

**Критерий готовности:** цепочка работает целиком, расшифровка и вопрос
проверяемы, сбой аудио не блокирует текст и скриншоты. Работы по этапу не
задерживают ближайший выпуск основных функций.

## Проверки и исполнение

Для изменений используются существующие `make check`, Go race tests,
frontend-тесты и [Windows-приёмка](../windows-acceptance.md). Для этапа 1 нужны
поддельные CLI/event fixtures: два запроса с разным порядком завершения, exec
с целым сообщением без частей, отмена, renderer reload и неизвестный исход,
ошибка контрольного сохранения и повтор только решения. Для потоковой ветки
дополнительно проверяются части, дубликаты и нарушенный порядок событий.
До её включения нужны проверки изоляции app-server с контрольной посторонней
конфигурацией и проверка продолжения существующей сессии; подмены событий
сами по себе изоляцию не подтверждают.
Проверки измеряют видимое поведение и восстановление, без настоящих LLM-вызовов
в CI. Изменения контрактов включают генерацию bindings и обновление Zod-схем.

[Исходный проект первой версии](../specs/solveo-design.md) сохраняет историю
проектирования. Этот roadmap задаёт дальнейший порядок и согласованные
изменения приоритетов; он не заменяет модульные `AGENTS.md` и технические планы.
Коммит и push требуют отдельного запроса; эксперимент не включает последующие этапы.
