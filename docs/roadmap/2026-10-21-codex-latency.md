# Codex: проверка задержки ответа

Дата: 2026-10-21. Ветка: `feat/parallel-answers`.
Среда: Windows Codex CLI 0.163.0, запуск из WSL2; время измерялось
монотонными часами снаружи Windows-процесса. Это диагностика, а не изменение
транспорта приложения.

## Что проверили

В пользовательских тестах быстрый ответ занял 41,241 и 40,163 с,
основной — 56,006 и 52,735 с. Эти значения включают весь вызов адаптера.
Они сами по себе не показывают время вычисления модели.

Отдельный диагностический запрос: `gpt-6-luna`, `low`, без изображения,
«Ответь только словом OK. Не используй инструменты.». Для `exec` использованы
те же основные параметры, что в приложении: `--json`, `--ignore-user-config`,
`--skip-git-repo-check`, `--sandbox read-only`, `--output-last-message`,
stdin и отдельная временная рабочая папка. `--ephemeral` отсутствует,
как и в адаптере сессий. Автоматического повтора запросов не было.

| Событие exec | Время от запуска |
| --- | ---: |
| Создан процесс | 0,011 с |
| `thread.started` | 5,392 с |
| `turn.started` | 10,514 с |
| `item.completed`, `agent_message` | 24,824 с |
| `turn.completed` | 24,889 с |
| Замечен файл итогового ответа | 29,553 с |
| Закрыты stdout/stderr | 39,582 с |
| Завершён процесс | 39,586 с |
| Удалена временная папка | 39,594 с |

Таким образом, после сообщения о завершении ответа прошло ещё 14,697 с
до выхода процесса. Удаление папки заняло около 8 мс. Текущий `runSession`
возвращает ответ после `cmd.Wait`, поэтому задержка завершения процесса
попадает во время ответа приложения. Внутренняя причина задержки выхода CLI
этим измерением не установлена. Принудительно завершать процесс сразу после
текста нельзя без отдельной проверки сохранения сессии и обработки ошибок.

## App-server

В отдельном stdio-процессе: `initialize`, `initialized`, диагностические
`config/read`, `skills/list`, затем `thread/start` и два последовательных
`turn/start` с тем же коротким вопросом. Пользовательский профиль сохранён.

- Handshake: 0,190 с от запуска.
- Создание потока: завершено к 5,660 с от запуска.
- Первый запрос: первая текстовая часть через 18,525 с от отправки,
  завершение через 18,643 с; с учётом подготовки — 24,303 с от запуска.
- Второй запрос в том же потоке: первая часть через 6,624 с,
  завершение через 6,724 с от отправки.
- После закрытия stdin процесс завершился примерно за 114 мс.

Это подтверждает возможность получать ответ без ожидания выхода процесса.
Один прогретый запрос не доказывает такую же скорость на скриншотах или при
двух одновременных запросах. Ускорение второго запроса нельзя целиком
приписывать транспорту: изменились состояние сессии и условия кэширования.

## Изоляция

`exec --help` описывает `--ignore-user-config` как пропуск `config.toml`,
с сохранением авторизации через `CODEX_HOME`. В реальном диагностическом
exec-запросе по-прежнему присутствовали каталог skills около 22,7 тыс.
символов и пользовательский блок `AGENTS.md` около 7,4 тыс. символов.
Это не полная изоляция инструкций.

App-server с обычным профилем обнаружил 4 MCP-настройки, 22 записи плагинов,
37 skills и пользовательский `AGENTS.md`. Это количество настроек/обнаруженных
skills, а не доказательство успешного запуска каждого MCP или плагина.

Отдельный временный `CODEX_HOME`, установленный именно в Windows-процессе,
дал 0 MCP-настроек, 0 записей плагинов и пустой `instructionSources`.
Но остались 6 skills: один общий из `.agents/skills` и пять встроенных.
Временный конфиг с `project_doc_max_bytes=0` и явными
`skills.config=[{path=".../SKILL.md",enabled=false}, ...]` отключил все шесть:
`skills/list` подтвердил `enabled=false` для каждого. Создание потока
завершилось к 0,657 с, включая запуск PowerShell-обёртки.

Машинный слой конфигурации по-прежнему присутствует в списке слоёв.
Полная независимость от машинной политики не доказана и не обещается.
В отдельной папке нет авторизации: `account/read` вернул `account=null`
и `requiresOpenaiAuth=true`. Секреты не копировались. Генерация и продолжение
сессии в изолированном режиме **не проверены**. Настройки, авторизация и
данные чатов пользователя не изменялись; CLI создавал диагностические сессии.

## Решение по результатам

Для следующего эксперимента обоснован постоянный app-server с отдельным
состоянием Solveo и собственной авторизацией. До замены адаптера нужно
проверить изолированную генерацию, фактические инструкции первого запроса,
точное продолжение сессии после перезапуска, отмену и неизвестный исход.
Затем сравнить один потоковый ответ с двумя параллельными на одинаковых
скриншотах. Не включать новый транспорт по умолчанию до этих проверок.

## Изолированный app-server: прототип

Отдельный Windows-прототип (вне репозитория) запускал `codex app-server` по
stdio с отдельным `CODEX_HOME`, пустой рабочей папкой, `-c model_provider="openai"`,
`-c project_doc_max_bytes=0`, `sandbox=read-only`, `approvalPolicy=never`.
Вход — device code через `account/login/start` этого же app-server; авторизация
пользователя и его профиль не копировались. Проверка инструкций — по записи
сессии (`thread.path`), а не только по `instructionSources`.

Подтверждено:

- Текст, снимок (`localImage`) и уточнение в одном thread работают; ответ по снимку верен.
- `thread/resume` в новом процессе возвращает тот же thread ID и сохраняет контекст.
  Несуществующий ID — ошибка `-32600: no rollout found`, новая сессия не создаётся.
- Два thread одновременно активны в одном процессе. `turn/interrupt` одного даёт
  `status=interrupted`, второй завершается, следующий turn проходит. После закрытия
  stdin процесс выходит за 0,1–0,3 с, `codex.exe` не остаётся.
- Текст приходит `item/agentMessage/delta`; у всех ответов `phase=final_answer`.
  Поле `phase` бывает `commentary`/`partial_answer`/`null`, поэтому промежуточный
  текст нельзя считать ответом без проверки.

Ограничения изоляции:

- После входа учётная запись ChatGPT загружает удалённые плагины
  (`openai-curated-remote`) в кэш отдельного `CODEX_HOME`. В запрос попали
  `<skills_instructions>` ≈19 тыс. символов (skills плагинов) и
  `<recommended_plugins>`; запустились MCP плагинов. `skills/list` этих skills не
  показывает и отсутствие skills не доказывает.
- `--disable plugins,remote_plugin,apps,tool_suggest,recommended_plugins,…` и
  `include_apps_instructions=false` убрали skills, плагины и MCP из запроса.
  Пользовательские skills отключены `skills/config/write`.
- Остаются встроенные блоки Codex: base instructions (18,4 тыс. символов),
  permissions, collaboration_mode, `multi_agent_role/mode` (≈2,7 тыс.; флагами
  `multi_agent*` не отключаются) и `environment_context`. Пользовательского
  содержимого в них нет.
- Машинный слой `C:\ProgramData\OpenAI\Codex\config.toml` загружается (сейчас пуст).
- По умолчанию `cli_auth_credentials_store="file"`: токен лежит в `auth.json`
  внутри отдельного `CODEX_HOME`.

Задержка (единичные прогоны, `gpt-6-luna`/`low`, короткие вопросы):

| Шаг | Время |
| --- | ---: |
| Запуск и handshake процесса | 0,15–0,4 с |
| `thread/start`/`thread/resume` | 5,07 с; 0,05 с со статическим каталогом |
| Первый turn нового или возобновлённого thread | 18–24 с; 16–17 с с каталогом и reasoning в `thread/start` |
| Следующий turn в том же thread | 5,5 с; 2,3 с с каталогом |
| Turn со снимком в прогретом thread | 7,9–8,2 с (без каталога) |

5,07 с — таймаут онлайн-обновления каталога моделей (`failed to refresh available
models: request timed out`): в отдельном `CODEX_HOME` нет `models_cache.json`,
обновление не удаётся, кэш не появляется, повторяется при каждом thread и turn.
Такой же шаг около 5 с виден в exec с обычным профилем (`thread.started` 5,39 с).
`model_catalog_json` с каталогом убирает ожидание; источник каталога для
приложения не решён (копирование из пользовательского профиля не допускается).

Холодный первый turn относится к thread, а не к процессу: новый thread в
прогретом процессе снова стоит 16–21 с. По журналу: websocket к
`chatgpt.com/backend-api/codex/responses` ≈4 с, прогревочный запрос Codex ≈4,5 с,
`world_state.build` ≈4,8 с, затем модель. Постоянный процесс ускоряет уточнения
в уже загруженном thread; новые чаты и быстрый ответ параллельного режима
(всегда новый thread) эту цену платят каждый раз.

## Сравнение транспортов в реализации

Ручной прогон адаптера Solveo (`codex.Client.Generate`, без UI) на Windows CLI
0.163.0: `gpt-6-luna`/`low`, одинаковый снимок, преднастройка и вопросы; 3 повтора,
30 запросов, сбоев нет. exec использует обычный профиль пользователя, app-server —
отдельный `CODEX_HOME` с keyring. «Подготовленный» — процесс запущен заранее
(`Prepare`), «прогретый» — уже обслужил предыдущий чат. Время до готового ответа,
медиана [мин–макс], с:

| Вариант | Новый чат со снимком | Уточнение |
| --- | ---: | ---: |
| exec | 49,7 [48,3–56,4] | 52,0 [48,5–52,4] |
| app-server, подготовленный процесс | 27,7 [26,7–27,9] | 5,6 [5,6–5,6] |
| app-server, прогретый процесс | 26,7 [26,7–26,9] | 5,6 [5,6–5,6] |
| Параллельно: подход | 26,7 [26,5–27,8] | 27,7 [27,6–27,8] |
| Параллельно: решение | 27,4 [26,7–28,0] | 5,6 [5,6–5,8] |

Ответы короткие: первый текст приходит за ~0,1 с до завершения. В отдельной
проверке длинного ответа первый текст пришёл через 5,7 с, ответ отменён через 7 с;
отмена подтверждена, соседний запрос и процесс не пострадали.

Выводы:

- app-server быстрее exec примерно вдвое на новом чате и в ~9 раз на уточнении:
  нет ожидания выхода процесса, thread остаётся загруженным.
- Холодная цена нового чата (~21 с turn + 5 с `thread/start`) не зависит от
  прогрева процесса. Прогрев процесса скрывает только запуск (~2 с) и первый
  `account/read` (~5 с), которые Solveo выполняет в фоне.
- Параллельный режим на app-server не даёт раннего подхода: на новом чате подход
  приходит одновременно с решением, на уточнении он в ~5 раз медленнее, потому что
  всегда открывает новый thread. При этом он удваивает расход лимита.
- Рекомендация по измерениям: для проверки пользователем — один потоковый ответ
  через app-server; параллельный режим на app-server не включать по умолчанию.
  Ускорение нового чата требует отдельной работы с каталогом моделей (5 с) и
  холодным turn, а не транспорта. Качество ответов этот прогон не оценивает.
