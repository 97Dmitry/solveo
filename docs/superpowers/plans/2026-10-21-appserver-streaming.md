# План: экспериментальный потоковый транспорт Codex app-server

**Цель:** показывать текст ответа до завершения процесса Codex. Итог 2026-10-21: после проверки на Windows пользователь сделал app-server единственным транспортом; exec, переключатель и состояние v1 удалены.

**Основание:** прототип из [замеров задержки](../../roadmap/2026-10-21-codex-latency.md#изолированный-app-server-прототип): изолированная генерация, снимок, уточнение, точное продолжение после перезапуска, два активных thread и `turn/interrupt` работают на Windows CLI 0.163.0.

**Решения пользователя (2026-10-21):** таймаут каталога моделей (5 с) в первой версии принимаем и отдельно ищем причину. Авторизация хранится в keyring Windows, если это подтвердит проверка, иначе в `auth.json` с оговоркой в документации. Вход — кнопка в настройках (device code через app-server).

## Ограничения

- Ветка `feat/parallel-answers`, без commit/push. Существующие незакоммиченные изменения сохраняются.
- Новый транспорт не включается по умолчанию; exec не удаляется.
- Нельзя копировать пользовательские `auth.json`, сессии, профиль и каталог моделей.
- Тесты используют только поддельный app-server. Настоящие запросы — только в ручных замерах.
- Не показывать рассуждения модели и `commentary`; частичный текст не считается ответом.
- Сохраняются правила архивации и параллельных ответов из `internal/app/AGENTS.md`.

## Архитектура

**Состояние Solveo.** `solveo-data/codex-home` используется как `CODEX_HOME`, `solveo-data/codex-work` — пустой рабочей папкой. При запуске передаются аргументы `-c model_provider="openai"`, `-c project_doc_max_bytes=0`, `-c include_apps_instructions=false` и `--disable plugins,remote_plugin,apps,tool_suggest,recommended_plugins,image_generation,browser_use,computer_use,in_app_browser,goals,daemon_auto_start`. Хранилище авторизации задаётся по результату задачи 0. Когда соединение готово: `skills/list(forceReload)`, затем отключение найденных skills через `skills/config/write` и повторная проверка. Если остался включённый skill или установлен плагин, генерация завершается ошибкой.

**Пакет `internal/llm/codex/appserver`** (свой `AGENTS.md` и `CLAUDE.md`):
- `Manager` с состояниями stopped → starting → ready → failed/closed: один процесс, ленивый запуск или фоновая подготовка без LLM-запросов. После сбоя следующий вызов перезапускает процесс; прерванное задание повторно не отправляется.
- Один цикл чтения stdout. Строка не длиннее 8 МиБ, повреждённый JSON переводит соединение в failed. Запись в stdin сериализуется mutex; ID запросов возрастают монотонно; таблица ожидающих ответов закрывается с ошибкой при разрыве.
- Таймауты: запуск и handshake 20 с, RPC 30 с, turn — существующий `Timeout` (10 мин), подтверждение interrupt 10 с, закрытие 5 с, затем `taskkill /T`.
- Маршрутизация уведомлений по `threadId`/`turnId`. События, пришедшие до ответа `turn/start`, буферизуются по thread. Чужие и поздние turn отбрасываются.
- На запросы сервера (approval и др.) отвечаем ошибкой: sandbox read-only, approval never.
- Итог turn: `completed` даёт текст последнего `agentMessage` из `item/completed` с фазой `final_answer` или `null`. `interrupted` после нашего interrupt даёт `context.Canceled`. `failed` — ошибка. Разрыв соединения, отсутствие подтверждения отмены или переполнение лимита текста (1 МиБ) — `ErrOutcomeUnknown` с сохранением известного thread ID.

**Codex `Client`.** Поля конфигурации копируются как сейчас. Объект управления процессом хранится в `Client` по указателю, общий для всех копий: mutex и соединение не копируются. Для этого инварианта есть тест.

**Состояние чата.** Версия 1 (`session_id`) всегда идёт через exec. Версия 2 — `{"version":2,"transport":"app_server","thread_id":…}`. Новый чат получает версию 2, только если включён экспериментальный транспорт. Чат версии 2 при выключенном транспорте получает явную ошибку и не переводится на exec. Отсутствующий thread даёт ошибку от `thread/resume`, новый не создаётся. Быстрый запрос использует `ephemeral:true` и не возвращает состояние. Reasoning задаётся и в `thread/start`/`resume`, чтобы прогрев Codex совпал с параметрами turn.

**Контракт `llm`.** `Event{Kind, Text}` с явными видами `progress` и `answer_text`. Для `answer_text` в `Text` лежит полный накопленный текст текущего блока, а не дельта, поэтому повтор и пропуск обновлений безопасны. Exec выдаёт только `progress`.

**Приложение.** Каждый вызов Generate получает обработчик, привязанный к operation ID, attempt ID и блоку (`message`/`approach`/`solution`). Предпросмотр хранится в контроллере вне документа чата и архива. В Wails он уходит отдельным событием `solveo:stream` с ревизией, не чаще одного раза в 100 мс на блок. Привязанный метод `StreamSnapshot` нужен для перезагрузки renderer и генерации DTO. Обновления устаревших operation/attempt и уже завершённых блоков отбрасываются. Статус ответа меняется только по итогу Generate; сохранение и очистка источников работают как сейчас.

**Измерения.** Адаптер пишет в нативный журнал одну строку на запрос, без содержимого: transport, purpose, процесс запущен и готов, thread готов, turn отправлен, первая часть, первые ≥80 символов или перевод строки, turn завершён. Контроллер добавляет время сохранения. Для exec — `thread.started`, `agent_message`, `turn.completed` и выход процесса.

**Интерфейс.** В настройках подключения: переключатель «Экспериментальный потоковый транспорт», состояние входа и кнопка «Войти» (ссылка и код, открытие через существующий bridge внешних ссылок, отмена). Предпросмотр в обычном сообщении и в блоках «Подход»/«Решение» помечен как незавершённый. Markdown рендерится тем же `react-markdown` (без HTML и удалённых изображений); незакрытый блок кода проверяется тестом.

## Задачи

0. **Keyring — выполнено 2026-10-21.** С новым `CODEX_HOME` и `cli_auth_credentials_store="keyring"` вход по device code, `account/read` после перезапуска и генерация работают; `auth.json` не создаётся, в Credential Manager появляется запись `LegacyGeneric:target=secrets|<hash>.codex`. Тот же home в режиме `file` учётной записи не видит. Предположение (не проверено): hash зависит от пути `CODEX_HOME`, поэтому перенос папки с EXE потребует нового входа.
1. **[x] Контракты:** виды `llm.Event`; state v2 и тесты отказов; поле транспорта в `settings.json` (необязательное, по умолчанию exec, схема 1 сохраняется).
2. **[x] `appserver`:** `Conn` (процесс, RPC), маршрутизация, лимиты; общий `appServer` в Codex-адаптере отвечает за жизненный цикл. Поддельный app-server на Go через повторный запуск тестового бинаря работает и на Windows.
   Тесты: перемешанные ответы и уведомления двух thread, частичные строки и повреждённый JSON, падение процесса до и после первой части, отмена одного turn при работающем втором, поздние события прежнего turn, resume точного ID и отказ на отсутствующем, Close без зависшего процесса.
3. **[x] Codex Client:** выбор транспорта по state и настройке, изоляция и проверка skills, вход и состояние учётной записи, измерения.
4. **[x] Контроллер:** обработчики потока, объединение обновлений, отбрасывание устаревших, `StreamSnapshot`, закрытие соединения в `Close`.
   Тесты: обычный и параллельный режим с частями; повтор только решения; поздний текст подхода после решения; ошибка сохранения и `RetrySave` без нового Generate; старые архивы и state v1 через exec.
5. **[x] Frontend:** Zod-схемы `solveo:stream` и учётной записи, проверенные по сгенерированным DTO; настройки и вход; предпросмотр. `make bindings`, frontend-тесты.
6. **[x] Документация:** README (вход, хранение, ограничения), `docs/windows-acceptance.md`, затронутые `AGENTS.md`. Затем `go test -race ./internal/app ./internal/history ./internal/settings ./internal/llm/...` и `make check`.
7. **Windows runtime и замеры:** замеры адаптера выполнены (см. [сравнение](../../roadmap/2026-10-21-codex-latency.md#сравнение-транспортов-в-реализации)); проверка UI на Windows ожидает пользователя. вход, снимки, поток, отмена, перезапуск, отсутствие процессов. Сравнение exec, одного потокового ответа и параллельного режима на одинаковых снимках, модели, reasoning и преднастройке. Холодные и прогретые запуски, новые чаты и продолжения отдельно; медиана и диапазон по нескольким повторам.

## Известные риски

- Первый turn каждого нового thread стоит 16–21 с из-за сети Codex. Параллельный быстрый ответ всегда открывает новый thread и может оказаться медленнее продолжения основного.
- Встроенные блоки Codex и машинный слой конфигурации не отключаются.
- `phase` бывает `null`; при нескольких `agentMessage` в turn предпросмотр показывает текущий элемент, итог берётся из завершённого финального.
- Протокол app-server помечен experimental: поля сверяются с JSON Schema установленной версии, неподдерживаемая версия CLI даёт понятную ошибку.
