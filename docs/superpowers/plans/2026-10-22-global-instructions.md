# Общие инструкции Solveo — технический план

**Цель:** общие инструкции в настройках, неизменяемый снимок для каждого нового локального чата и отсутствие повторной конфигурации в обычных вопросах.
**Основа:** master ffb16ab; текущий checkout, ветка feat/global-instructions. Публикация PR и слияние разрешены пользователем 2026-10-22.
**Спецификация:** раздел 2.1 docs/roadmap/2026-10-21-core-features.md и требования задачи от 2026-10-22.
**Стек:** Go, Wails v2, React/TypeScript, Zod, pnpm/Vite+.

## Решения и ограничения

- settings.Config.GlobalInstructions и chat.Chat.GlobalInstructions: UTF-8 текст до 16384 Unicode code points. Go использует utf8.RuneCountInString, TypeScript Array.from; не UTF-16 length. Старые JSON дают пустую строку. Атомарная запись остаётся storage.Replace.
- Снимок создаёт app, без зависимости chat от settings. Все четыре пути: запуск, NewChat, DiscardUnsaved, restoreWork отсутствующего чата. Даже пустые существующие чаты сохраняют свой снимок.
- llm.Request.GlobalInstructions передаёт снимок обоим запросам. Config/ConfigRevision по-прежнему заморожены в пользовательском ходе для retry.
- Установленный codex-cli 0.163.0: проверена локальная schema командой `codex app-server generate-json-schema --out /tmp/solveo-codex-schema`. ThreadStartParams и ThreadResumeParams содержат developerInstructions/baseInstructions; TurnStartParams не имеет прямой замены developerInstructions. [Исходник тега rust-v0.163.0](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/app-server/src/request_processors/thread_processor.rs) явно сообщает, что loaded thread игнорирует resume overrides. Поэтому не используем resume как обновление.
- Новый thread получает базовую инструкцию Solveo (Client.Prompt либо default), общий снимок и текстовую преднастройку через developerInstructions. Встроенная базовая инструкция Codex не заменяется. Модель/effort остаются параметрами thread/turn; purpose задаёт формат подхода/решения отдельно; developerInstructions явно закрепляет приоритет этого формата над пользовательскими пожеланиями.
- Непрозрачное состояние v2 расширяется подтверждённым SHA-256 инструкции и pending hash. Старое v2 без хеша при следующем вопросе получает явное обновление. Обычный вопрос содержит только вопрос, контекст standalone подхода и purpose, без всей конфигурации.
- Изменённая инструкция добавляется явным блоком обновления в тот же пользовательский ход; это сохраняет разговор, но прежний текст остаётся в истории. Блок явно заменяет предыдущие пожелания, преднастройка чата имеет приоритет над общими. Это не гарантия соблюдения конфликтующих инструкций моделью.
- Хеш подтверждается только завершённым успешным ходом, включая первый: thread/start ещё не доказывает сохранение model-visible контекста первого хода. При неизвестном исходе сохраняется pending, без автоматической отправки; только явная отправка пользователя может повторить неподтверждённое обновление; retry использует исходную конфигурацию. Отмена/ошибка не подтверждают новую версию. Restart с подтверждённым хешем не добавляет копию из-за resume.
- Никаких новых зависимостей, скрытых AGENTS в данных Codex, browser storage или реальных LLM в тестах.

## Проверка рисков

Проверить старые пустые чаты, восстановление отсутствующего архива, повтор после смены преднастройки, два независимых thread, ошибку и неизвестный исход обновления, продолжение с диска без дублирования. Провайдерский JSON разбирает только codex.

## Эксперимент короткой инструкции

Не завершён. Schema допускает baseInstructions на start/resume; по умолчанию это поле не передаём. До включения нужны отдельные реальные сравнительные запуски с одинаковой моделью/effort и задачами (теория, код, расчёты, снимки, уточнения): время до полезного текста/полного ответа, правильность, язык/формат, отсутствие tool calls. Сохранять read-only sandbox, approval never и отдельный CODEX_HOME. В тесты/CI реальные запросы не входят. Никакого вывода об ускорении без этих измерений.

## Результаты ревью и уточнения реализации

- Независимое ревью обнаружило потерю более нового черновика при подтверждении сохранения поля. Убрано перемонтирование по key; синхронизация сохранённой базы сохраняет dirty draft. Регрессия воспроизведена падающим тестом и исправлена.
- Обнаружен конфликт уровня developer-пожеланий с user-форматом предварительного подхода. Developer-инструкция теперь явно закрепляет приоритет формата Solveo (в частности подход без кода). Регрессионный тест проверяет реально отправляемый thread/start.
- Первоначальный thread/start не подтверждает долговечность инструкций: Codex откладывает initial context до первого реального хода (`core/src/session/mod.rs`, record_initial_history). При первом failed/unknown ходе остаётся pending; явный повтор восстановит пожелания, даже если первоначальный контекст не успел сохраниться.
- Выбран консервативный учёт: failed/canceled/unknown ход не подтверждает новую версию. Следующая явная отправка может повторить блок, который уже успел попасть в историю. Точно устранить такие повторы без подтверждения модели нельзя; нормальные успешные продолжения и resume копий не добавляют.
