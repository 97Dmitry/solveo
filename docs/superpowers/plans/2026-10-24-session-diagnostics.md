# Журнал диагностики сессии

Статус: реализовано в `claude/brave-thompson-v8btpv`; Windows-приёмка — раздел «Журнал диагностики» в `docs/windows-acceptance.md`. Тексты пишутся только при включённом переключателе «Записывать тексты вопросов, ответов и расшифровок» (по решению пользователя).

## Что есть сейчас

- Постоянного журнала нет. EXE собран как GUI: `log.Print` в
  `main_windows.go` (ошибка запуска, «native event queue full») уходит в
  отсутствующую консоль.
- `Controller.ReportError` хранит только последнюю строку ошибки для плашки;
  предыдущие теряются при следующей ошибке и при выходе.
- «Журнал запроса» — до 64 КиБ вывода CLI текущего запроса в памяти, в нативном
  окне (`operation.go: appendLog/flushLog`). На диск не пишется и после
  перезапуска пропадает.
- stderr Codex app-server намеренно отбрасывается, сохраняется только последняя
  строка `Error:` (`appserver/conn.go: errorLine`).
- Паника в любой горутине завершает процесс без следа. Падение дочернего окна
  аудио (`--audio-window`) видно только как исчезнувшее окно: его stderr и код
  выхода не сохраняются.
- Ошибки рендереров (исключения JS, отклонённые promise, падение React) нигде
  не фиксируются.
- Сборка не сообщает свою версию; `debug.ReadBuildInfo` уже содержит
  `vcs.revision`/`vcs.time`, если сборка шла из git.

## Цель

После сбоя пользователь открывает папку журналов или собирает архив
диагностики и получает хронологию сессии: что запускалось, какие операции шли,
сколько длились, какие ошибки и падения были. Журнал не содержит текста
вопросов, ответов, расшифровок, инструкций, ключей и токенов.

## Решение

### Модуль `internal/diagnostics` (новый, со своими `AGENTS.md` + `CLAUDE.md`)

- `Open(dir)` создаёт `solveo-data/logs/session-<UTC YYYYMMDD-HHMMSS>-<pid>.log`
  и возвращает `*slog.Logger` и `Close`. Формат — `slog.TextHandler`
  (`time=… level=… msg=… key=value`): читается глазами и разбирается
  программно. Время только UTC.
- Запись асинхронная: ограниченный канал и одна горутина-писатель. Вызов
  журнала никогда не блокирует вызывающего (в том числе под `c.mu`). Если канал
  переполнен, запись отбрасывается, а счётчик потерь попадает в следующую
  запись. Уровни `Error` и выше, а также `Close` сбрасывают буфер на диск.
- Лимит — 8 МиБ на сессию. После лимита пишется одна запись-маркер, дальше
  идут только `Error`.
- Хранение: при старте удаляются файлы `session-*.log` и `crash-*.txt` сверх
  последних 20 сессий. Удаление идёт через `os.Root` по точному шаблону имени,
  чужие файлы и симлинки не трогаются.
- Падения: `debug.SetCrashOutput(crash-<та же метка>.txt)` сохраняет трассу
  фатальной паники из любой горутины. В начало сессионного журнала пишется
  `previous_crash=<файл>`, если прошлая сессия оставила непустой crash-файл.
- Маскирование как вторая линия защиты: ко всем строковым значениям
  применяется маскировщик (`Bearer …`, `token=…`, `api_key`, `xai-…`,
  `AIza…`, `sk-…`, длинные base64/hex-последовательности). Первая линия —
  не передавать содержимое в журнал вовсе.
- Без Windows-зависимостей; тестируется на любом хосте.

### Что пишется

| Область | События (только метаданные) |
| --- | --- |
| Сессия | старт/выход, длительность, версия (`vcs.revision`, `vcs.time`, `vcs.modified`), Go, версия Windows, версия WebView2, флаги запуска без содержимого `--prompt-file`, код выхода |
| Запуск | этапы `run()` с длительностью: instance lock, history, workstate, host, Codex, окно аудио, DOM/renderer ready, первый показ; ошибка запуска (сейчас только MessageBox) |
| Ошибки | каждый `ReportError` с источником; `native event queue full`; ошибки хоткеев и захвата; ошибки сохранения и восстановления |
| Операции LLM | id, вид (submit/capture/check/followup), модель, effort, число снимков, длины текста в символах; время до первой части ответа, общее время; исход ok/cancel/error/uncertain |
| Codex app-server | запуск/завершение процесса, PID, код выхода, причина (уже отфильтрованная строка `Error:`), переподключения; транспорт сборщика вопросов отдельно |
| Аудио/STT | выбранный провайдер, старт/стоп, устройства (имена без идентификаторов), ошибки устройств, переподключения облачных сессий, состояния контейнера Qwen, переполнение и потери буферов |
| Сборщик вопросов | анализ: длительность, исход, переполнение, ошибки; без формулировок |
| Окно аудио | запуск дочернего процесса, PID, код выхода, последние ≤16 КиБ его stderr (туда пишется трасса паники Go), ошибки IPC |
| Рендереры | `window.onerror`, `unhandledrejection`, React error boundary: сообщение и стек, без DOM и текста полей |

Не пишется: словарь, инструкции и профили; содержимое «Журнала запроса»; ключи;
сырой stderr Codex; пути к снимкам (только их количество). Текст вопросов,
ответов, расшифровок и сформулированных сборщиком вопросов пишется только при
включённом переключателе `diagnostics.include_content` (по умолчанию выключен,
до 4096 символов на запись).

### Подключение

- `main_windows.go`: `diagnostics.Open` сразу после создания `solveo-data` и
  до `instance.Acquire`, чтобы ошибка блокировки тоже попала в журнал. Если
  журнал не открылся, приложение работает без него: ошибка журнала не мешает
  запуску. `startupError` и `log.Printf` переходят на логгер.
- `core.Dependencies.Log *slog.Logger` (nil → `slog.New(slog.DiscardHandler)`).
  Контроллер пишет из существующих точек: `ReportError`, жизненный цикл
  операции, сохранение, аудио, сборщик. Отдельных горутин не добавляет.
- `codex.New` и `appserver.Options` получают логгер для событий процесса. Сырой
  stderr по-прежнему не сохраняется.
- Окно аудио: родитель получает stderr дочернего процесса через pipe и
  кольцевой буфер 16 КиБ и пишет хвост в журнал при ненулевом коде выхода.
  Дочерний процесс файлов журнала не открывает. Ошибки его рендерера идут в
  родитель новой allowlisted-командой `diagnostic` (тело ≤ 16 КиБ, не чаще
  20 за 10 секунд и 500 за запуск); родитель пишет их в журнал.
- Wails: `options.App.Logger` — адаптер к slog, `LogLevel` Warning.
- Фронтенд: `frontend/src/app/diagnostics.ts` подписывается на
  `error`/`unhandledrejection`. React error boundary использует пакет
  `react-error-boundary` (поддерживается, широко распространён, около 1 КБ;
  добавляется через pnpm). Отправка через binding `ReportDiagnostic`
  (основное окно) или команду `diagnostic` (окно аудио), с ограничением частоты
  и размера на стороне клиента и повторной проверкой в Go.

### Интерфейс

Настройки → вкладка «Подключение» (рядом с «Журналом запроса»), раздел
«Диагностика»:

- «Открыть папку журналов» — Проводник на `solveo-data/logs`.
- «Собрать архив диагностики» — zip в `solveo-data/exports/diagnostics-<UTC>.zip`
  с журналами и crash-файлами последних 5 сессий и файлом `summary.txt`
  (версия, ОС, WebView2, выбранные провайдеры); затем открывается папка.
  Чаты, снимки, настройки с инструкциями и ключи в архив не попадают.
- Строка «Прошлая сессия завершилась аварийно» с кнопкой «Собрать архив»
  появляется один раз после запуска, если найден непустой crash-файл.

Окно аудио новых элементов не получает.

### Документация

- README, раздел «Настройки и данные»: папка `logs`, что пишется и что нет,
  срок хранения, архив диагностики.
- `docs/windows-acceptance.md`: падение дочернего окна аудио, аварийное
  завершение основного процесса (диспетчер задач не подходит — нужна паника;
  для проверки используется скрытый флаг `--diagnostics-test-panic`, который
  только вызывает панику после запуска), содержимое архива.
- Корневой `AGENTS.md`: ссылка на `internal/diagnostics/AGENTS.md`.

## Проверки

- `go test -race ./internal/diagnostics`: формат, UTC, неблокирующая запись
  при полном канале и счётчик потерь, лимит 8 МиБ и маркер, хранение 20 сессий
  без удаления чужих файлов и симлинков, маскирование, crash-файл прошлой
  сессии, состав архива.
- `go test -race ./internal/app`: логгер-подмена фиксирует события операций и
  ошибок; в них нет текста вопроса, ответа и расшифровки (проверка с уникальной
  меткой в содержимом).
- `go test -race ./internal/audiowindow`: команда `diagnostic` в allowlist,
  лимиты тела и частоты.
- Фронтенд: error boundary и глобальные обработчики вызывают мост с усечённым
  сообщением; ограничение частоты.
- `make check`.
- Windows-приёмка по новым пунктам `docs/windows-acceptance.md`.

## Вне объёма

Отправка журналов по сети, телеметрия, автоматическое обновление, настройка
уровня журнала в интерфейсе, сохранение «Журнала запроса» на диск.
