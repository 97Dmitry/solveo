# Этап 2.2 — ускорение первого ответа

**Цель:** измеримо сократить время до полезного текста нового чата, сохранив изоляцию и точное продолжение.
**Основа:** origin/master `1d77a97`, ветка `perf/stage-2.2-first-response`, текущий checkout. Без commit/push/PR/merge.
**Спецификация:** §2.2 `docs/roadmap/2026-10-21-core-features.md`, требования пользователя от 2026-10-22.
**Стек:** Go / Wails v2; установленный Windows Codex 0.163.0; fake app-server для тестов.

## Подтверждено кодом, ещё не измерением

- `Client.Prepare` / `app.prepareConnection` уже запускают процесс, изолируют skills/plugins и читают account в фоне. Новый Generate повторно проверяет account, затем вызывает thread/start и turn/start.
- Модель и effort задаются на thread и turn; developerInstructions содержат снимок общих инструкций и преднастройку. Успешный thread/start не подтверждает долговечность инструкций.
- Приложение создаёт локальный чат заранее; provider state появляется после Generate. Сохранение вопроса/PNG предшествует Generate. Переключение и изменение конфигурации сериализованы controller.
- Исторические 27/5–6 с и таймаут каталога требуют нового измерения. У установленного Solveo уже есть собственный models_cache.json; у старого экспериментального keyring-профиля его нет. Это разные профили, смешивать результаты нельзя.

## Гипотезы

- Обновление каталога не укладывается в 5 с и потому не сохраняет пригодный кэш; требуется проверить источник, identity/version/TTL, сетевое поведение установленной версии.
- Подготовка thread может скрыть thread/start, но не холодный первый turn. После исправления каталога выигрыш может оказаться недостаточным для дополнительного жизненного цикла заготовок.

## Проверка границ

Сохраняются CODEX_HOME/keyring/empty cwd/read-only/approval never; pending instructions после сбоя; exact resume и unknown без resend. Не включать parallel и baseInstructions override. Измерения адаптера не заменяют приёмку Windows UI/capture. Никаких прямых мутаций data-store: профиль изменяет только штатный Codex через проверенный адаптер.

## Уточнение после измерений

- Штатный app-server уже обновляет каталог при запуске и каждые 270 с. В текущей серии remote fetch успешен, кэш появился самостоятельно; повторные thread/start 61–78 мс. Дополнительный model/list/статический каталог в продукте не нужен. Исторический таймаут подтверждён исходником и журналом, текущая причина отсутствия прежнего кэша — незавершившийся fetch, а не перенос/права/формат.
- Пять чередующихся пар immediate/prepared (2 с ввода до вопроса): медиана TTFT 3,060 → 1,926 с; один prepared выброс 34,525 с, причина не установлена. Выигрыш медианы оправдывает проверку реализации, не обещание верхней границы.
- Пользователь явно разрешил штатный Responses prewarm с generate=false. Это сетевой запрос, но не model generation и не turn/start.
- Реализация: `llm.ChatPreparer.PrepareChat(ctx, ChatPreparation)` владеет заготовкой до отмены или потребления; `Request.ChatID` связывает её с локальным чатом. `codex/preparation.go`: один slot + gate, ключ chat ID/instructions hash/model/effort, connection pointer; ожидание конкурирующего start вместо дублирования; освобождение исходного connection через unsubscribe. `app/preparation.go`: context/waitgroup controller, отмена при смене чата/конфига/выходе, снимок конфигурации под mutex. State не сохраняется до Generate. Ошибки подготовки разрешают обычный start, поскольку turn ещё не отправлялся; неизвестный исход Generate не повторяется.

## Проверка реализации и ревью

- Fake tests: одновременные process Prepare/Generate и thread PrepareChat/Generate, единственное потребление, pending первого хода, несовпадение chat/instructions/model/effort, отмена неиспользованного и незавершённого start, ограничение ресурсов, restart, unknown без resend, no background turn, конец приложения, actual controller → fake app-server → archive → restart с exact ID.
- Независимое ревью выявило гонку retirement: старый cleanup мог убить процесс нового/возобновлённого вопроса или Check. Регрессия RED на всех трёх путях; исправлены published-through-cleanup + finished barrier, foreground reservation и reconnect до turn/start. Focused race GREEN.
- После успешного login/Check подготовка пустого чата теперь возобновляется. Обе регрессии прошли RED→GREEN.
- Повторное ревью выявило потерю claimed ID при раннем account error/account=null/cancel. Три регрессии прошли RED→GREEN; ownership сразу передаётся в возвращаемые thread ID/pending, успешный первый ход подтверждает hash. Финальное узкое ревью новых находок не дало.
- Реальные Windows серии и полный диапазон, включая 429/backoff, сохранены в latency report и `docs/measurements/2026-10-22-first-response/`. Новый чат выигрывает 25–37% по медиане, но отсутствие замедления уточнений контрольные серии пока не подтвердили. Первоначально решение о сохранении заготовок было запрошено у пользователя; затем он явно подтвердил сохранение и допустимость небольшой разницы уточнений.
