# Сборщик вопросов интервью — технический план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Работа в текущем checkout, без коммитов и публикации.

**Goal:** собирать проверяемую карточку из новых окончательных ASR-реплик и отправлять её только по явному действию.

**Architecture:** ограниченный автомат состояний `internal/questionbuilder`, прикладной контроллер Go, отдельная optional capability `llm.QuestionAnalyzer`. Codex использует ленивый вспомогательный app-server с тем же Solveo CODEX_HOME: его отмена/неизвестный исход не затрагивают основной транспорт и подготовку. Подтверждённая отправка проходит существующий submit с отдельным origin и метаданными карточки в пользовательском сообщении.

**Tech Stack:** существующие Go/Wails, React/TypeScript/Zod, компоненты проекта; новых зависимостей нет.

**Spec:** `docs/superpowers/specs/2026-10-23-interview-question-builder-design.md`.

## Ограничения и уточнения

- Включение только явно, только новые final; системный источник обязателен. Сохранённая ручная версия заморожена и может быть отправлена при новых репликах.
- debounce 800 ms, интервал стартов ≥2 s, один запрос, timeout 15 s; ошибки без автоматического повторения.
- Окно 120 s / 80 final / 16000 Unicode-символов; карточка ≤8000 символов / 80 оснований. Переполнение необработанных данных — видимая остановка, без потери остатка.
- Карточка владеет копиями исходных реплик, независимо от эфира/очистки/архива. На диск попадают только принятые версии вместе с сообщением; неподтверждённые карточки остаются в RAM.
- Ссылка уточнения хранит ID предыдущего отправленного пользовательского вопроса отдельно от `reply_to_id` (ссылка на ответ). Модель явно сообщает, является ли вопрос уточнением; родитель разрешает ссылку только на последний отправленный вопрос этого чата.
- Возврат в чат не включает анализ. Новые системные реплики после отключения делают автоматическую карточку несвежей; вручную сохранённую можно отправить. Исходные utterance, начатые до включения, не становятся новым вопросом после позднего final.
- При переполнении/ошибке доступна ручная правка и пропуск. «Нет вопроса» не может молча удалить существующую карточку: продолжение должно вернуть обновлённый текст либо сохранить предыдущую.
- Согласованная компоновка: карточка над транскрипцией отдельного аудиоокна, источники раскрываются; модель/effort в свёрнутых настройках.

## Review Focus

- Начало системной речи между показом карточки и отправкой: проверка готовности атомарна с принятием submit.
- Пропуск во время анализа: инвалидирует весь снимок, сохраняя более поздние реплики.
- Редактирование до прихода ответа: результат не перезаписывает пользовательский текст.
- Очистка эфира и смена чата: исходные тексты карточки сохраняются, межчатовые результаты отвергаются.
- Сбой анализа одновременно с основным ответом: основной транспорт и подготовка продолжают работу.

## Исправления после пользовательского прогона 2026-10-23

Проблемы: эффективные apps/plugins/browser flags сборщика оказались включены;
краткая формулировка вопроса потеряла существенный признак записи в общую мапу.

Рекомендация и границы исправления:

1. Ограничения анализатора задаются dotted CLI overrides / --disable при запуске
   только вспомогательного процесса. Thread config не заменяет таблицы features/tools.
   Fake-тест проверяет реальную границу аргументов запуска и отсутствие замен таблиц;
   установленный Codex проверяется без model turn и без пользовательских credentials.
2. Инструкция сборщика требует минимальных редакторских изменений и сохранения
   операций, отрицаний, чисел, типов и условий. Семантическую полноту нельзя
   гарантировать словарём ключевых слов или тестом fake-модели.
3. Автоматический вопрос передаёт основной/approach-модели оригинальные основания
   как недоверенные данные рядом с формулировкой. Общий бюджет оснований карточки —
   16000 Unicode-символов, без тихого усечения; переполнение не продвигает границу.
   Additive Card.origin (automatic/manual) фиксирует происхождение; ручные и legacy-версии без признака не дополняются старыми условиями
   автоматически. Retry/архив сохраняют этот признак.
4. Регрессии: сокращённый вопрос про memory access сохраняет исходное write-условие
   в обоих provider payload; ручная версия не получает отменённые исходные условия;
   union выше бюджета отклоняется целиком. Bindings генерируются, Zod обновляется.
5. Проверки: targeted RED/GREEN, make check, race по затронутым модулям и diff check.
   Прежние Windows данные не изменяются; новый runtime/качество проверяет пользователь.

## Черновик после завершённого анализа — исправление UX

Пользовательский прогон: последний анализ 2026-10-23T17:10:13Z завершился за
3.088 s, активных model turns в логах нет. Все реплики окончательные, UI показывает
«Уточняю условия», отправка выключена. Состояние draft не является выполняющимся
анализом, но прежняя формулировка скрывает это различие.

- Состояние draft называется «Черновик вопроса», с явным пояснением ожидания
  продолжения либо проверки человеком. Только analyzing обозначает работающий запрос.
- Go выдаёт can_confirm лишь для непустой модели-черновика после анализа, без
  ошибки, незавершённой/необработанной системной речи, ручного редактирования и gap.
  Явная команда confirm превращает именно показанную ревизию в замороженную
  подтверждённую версию; происхождение текста не меняется, чтобы сохранить передачу исходных условий автоматической карточки. Команда не отправляет вопрос и не вызывает модель.
- UI показывает «Подтвердить этот текст» по can_confirm, отдельно от отправки.
  Существующие edit/save остаются способом исправить текст и явным исключением
  свежести. Таймаут/пауза никогда не переводят черновик в готовый автоматически.
- Инструкция модели различает законченные самостоятельные вопросы и общее
  объявление будущей темы, которое само по себе не делает уже заданное неполным.
- Регрессии: завершённый ready=false → явное подтверждение без provider call;
  подтверждение блокируется при partial/new final/анализе/ошибке/gap; поздняя речь
  остаётся хвостом; UI не показывает draft как работающую модель. Bindings/Zod
  обновляются вместе. Затем make check и race по затронутым пакетам.
