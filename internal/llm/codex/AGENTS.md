# Codex adapter

- All requests, the connection check and model discovery use one persistent `codex app-server` per application (`transport.go`), started in the background without a model turn and restarted on the next call after a failure — never resubmitting earlier work. There is no `codex exec` path. Uncertain outcomes retain the known thread state.
- Isolation: `CODEX_HOME=solveo-data/codex-home`, an empty `codex-work` cwd, `isolationArgs` (keyring auth, `project_doc_max_bytes=0`, plugins/remote_plugin/apps and similar features disabled) and every skill from `skills/list` disabled and re-verified at start. After login the account syncs remote plugins whose skills/MCP reach the prompt unless those features are disabled, and `skills/list` does not show them: verify isolation from the rollout's actual model input, not `instructionSources`. Built-in Codex instructions and the machine config layer remain. Never copy the user's auth, sessions, profile or model cache.
- `codex-home` must be on a local disk (`localDisk`): Codex cannot open its SQLite state on UNC paths such as `\\wsl.localhost`. Only the last `Error:` line of stderr is surfaced; raw stderr and account data (e-mail, plan) never leave the adapter. Windows cancellation still terminates the launcher tree via `taskkill /T`.
- Chat state is `{"version":2,"transport":"app_server","thread_id"}`; anything else is rejected without starting a process. Resume preserves the exact thread ID; a missing thread is an explicit error, never a new thread. Threads loaded in the current process are continued without another `thread/resume`.
- Parallel answers: only the solution continues the chat thread; the approach (and the connection check) uses an ephemeral thread released with `thread/unsubscribe` and returns no state. Prompt purpose selects short no-code approach or independently checked solution; empty purpose is the ordinary main solution and must receive the same task-dependent code/answer instructions; model/effort are turn parameters and also set on the thread so Codex reuses its warm-up.
- Model discovery uses `model/list` on the same connection, paginated and bounded, preserving advertised effort order/defaults and rejecting malformed metadata. Codex may serve its cached/bundled catalog; do not claim a guaranteed fresh list.
- Text arrives as `item/agentMessage/delta` previews (`llm.EventAnswerText`); only the completed final item is the answer. Timing lines in the log carry no content. The login is a device code via `account/login/start`; a completion may arrive before the start reply and is kept until the login registers.
- Measurements and isolation evidence: `docs/roadmap/2026-10-21-codex-latency.md`. Tests use the re-executed Go fake in `appserver/appservertest`; run `go test -race ./internal/llm/codex/...`.

- State v2 additionally carries `instructions_hash` and `pending_instructions_hash`. New threads receive Solveo/user preferences in developerInstructions; normal turns omit them. Codex 0.163.0 ignores resume overrides for loaded threads, so changed preferences use an explicit user-turn update, authorized by the initial instruction. Confirm its hash only after successful completion (including the first turn; thread/start alone does not establish durable initial context); failed/unknown updates retain pending, and only an explicit user submission may resend them. Resume alone never reapplies instructions. Hash excludes model/effort/purpose. Client.Prompt remains the Solveo base; do not set baseInstructions by default.
- If the latest user turn in Request.History did not complete successfully, distrust the archived applied hash: the app may have crashed after Codex accepted changed preferences but before provider state was saved. Synchronize current instructions on the next explicit submission; do not resubmit the interrupted question automatically. A later successful turn restores ordinary hash-based deduplication.

- `preparation.go` owns one empty-chat thread, including in-flight start and cleanup (gate), bound to local ChatID + instruction hash + model/effort and the exact Conn. PrepareChat blocks its background worker until claim/cancel/process loss; matching Generate waits for start and atomically takes it. Ephemeral approach/check and existing state never consume it. A late worker is suppressed by lastSubmittedChat. Cancellation of thread/start collects its reply with a bounded independent context before unsubscribe; an unaddressable start or unconfirmed release retires the process to preserve the resource bound. Close/login changes invalidate it. No preparation state enters Solveo history; initial instruction hash is still pending until a successful real turn.
- Codex 0.163.0 already refreshes the full model catalog at startup and every 270 s; TTL is 300 s, scoped to client version and credential identity. A failed 5 s fetch does not populate cache; the current environment now fetches successfully. Do not add another refresh loop or a handcrafted/static picker-derived catalog. See the 2026-10-22 section of the latency report for fresh measurements and limitations.
- Every foreground run reserves `foreground` before a late preparer can register. All paths (new, resume, check, approach) settle stale preparation before using the connection; `finished` closes only after cleanup/retirement. Reconnect, if needed, happens before any model turn. A claimed thread immediately transfers to the result's thread ID + pending instruction hash, so early account errors/cancellation cannot lose its ownership. The successful continuation path adds no provider RPC.

- Follow-ups quote the exact selected answer from Request.History in prompt JSON referenced_answer (local message_id, optional kind, text). Validate the reference before launch; never silently redirect an unresolved reference to the latest answer. Send only this selected quote, not the full history again; instruction hashes/provider state remain unchanged.

- Interview Position/Stack/InterviewFormat/Experience belong to stable instruction JSON and its hash, not the ordinary question. Omit empty interview fields for legacy defaults. Both main/approach receive the frozen Config; instructions explicitly forbid invented candidate experience, with clarification or a labeled draft when facts are missing. This is model guidance, not a factuality guarantee.

- `Turn.FromTranscript` appends per-turn speech interpretation guidance to ordinary/approach/solution prompts. Keep it outside stable instructions/hash; preserve the original question and do not label ordinary typed messages as transcription.

- `question.go` uses a second lazy app-server with the same Solveo CODEX_HOME and its own transport lifecycle. This is an intentional exception to the single main app-server above: an analysis cancellation/failure cannot retire the main prepared thread or answer. Each request is ephemeral, has dedicated base/developer instructions and outputSchema, and returns no state. Apply analysis-only tool/feature restrictions in process CLI arguments, preserving the common isolation flags; never replace whole features/tools tables in thread/start.config (those overrides can restore default apps/plugins). Only model/effort are thread overrides; never inherit answer instructions. Fake tests verify wire configuration/lifecycle; actual model input/tool exposure still requires runtime inspection after Codex upgrades. Close drains workers before closing both transports.

- `question_context.go` enriches only new OriginAutomatic cards with exact source text, ordered by Seq, and does the same for an explicitly referenced prior automatic question. Total source evidence is bounded to 16000 runes per card / 80 rows before Generate; no truncation. OriginManual and legacy missing origin send only their accepted question text, never canceled source conditions. This is deterministic evidence preservation, not a semantic completeness guarantee for the LLM's wording.
