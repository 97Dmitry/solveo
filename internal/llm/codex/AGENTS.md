# Codex adapter

- All requests, the connection check and model discovery use one persistent `codex app-server` per application (`transport.go`), started in the background without a model turn and restarted on the next call after a failure — never resubmitting earlier work. There is no `codex exec` path. Uncertain outcomes retain the known thread state.
- Isolation: `CODEX_HOME=solveo-data/codex-home`, an empty `codex-work` cwd, `isolationArgs` (keyring auth, `project_doc_max_bytes=0`, plugins/remote_plugin/apps and similar features disabled) and every skill from `skills/list` disabled and re-verified at start. After login the account syncs remote plugins whose skills/MCP reach the prompt unless those features are disabled, and `skills/list` does not show them: verify isolation from the rollout's actual model input, not `instructionSources`. Built-in Codex instructions and the machine config layer remain. Never copy the user's auth, sessions, profile or model cache.
- `codex-home` must be on a local disk (`localDisk`): Codex cannot open its SQLite state on UNC paths such as `\\wsl.localhost`. Only the last `Error:` line of stderr is surfaced; raw stderr and account data (e-mail, plan) never leave the adapter. Windows cancellation still terminates the launcher tree via `taskkill /T`.
- Chat state is `{"version":2,"transport":"app_server","thread_id"}`; anything else is rejected without starting a process. Resume preserves the exact thread ID; a missing thread is an explicit error, never a new thread. Threads loaded in the current process are continued without another `thread/resume`.
- Parallel answers: only the solution continues the chat thread; the approach (and the connection check) uses an ephemeral thread released with `thread/unsubscribe` and returns no state. Prompt purpose selects short no-code approach or independently checked solution; model/effort are turn parameters and also set on the thread so Codex reuses its warm-up.
- Model discovery uses `model/list` on the same connection, paginated and bounded, preserving advertised effort order/defaults and rejecting malformed metadata. Codex may serve its cached/bundled catalog; do not claim a guaranteed fresh list.
- Text arrives as `item/agentMessage/delta` previews (`llm.EventAnswerText`); only the completed final item is the answer. Timing lines in the log carry no content. The login is a device code via `account/login/start`; a completion may arrive before the start reply and is kept until the login registers.
- Measurements and isolation evidence: `docs/roadmap/2026-10-21-codex-latency.md`. Tests use the re-executed Go fake in `appserver/appservertest`; run `go test -race ./internal/llm/codex/...`.

- State v2 additionally carries `instructions_hash` and `pending_instructions_hash`. New threads receive Solveo/user preferences in developerInstructions; normal turns omit them. Codex 0.163.0 ignores resume overrides for loaded threads, so changed preferences use an explicit user-turn update, authorized by the initial instruction. Confirm its hash only after successful completion (including the first turn; thread/start alone does not establish durable initial context); failed/unknown updates retain pending, and only an explicit user submission may resend them. Resume alone never reapplies instructions. Hash excludes model/effort/purpose. Client.Prompt remains the Solveo base; do not set baseInstructions by default.
- If the latest user turn in Request.History did not complete successfully, distrust the archived applied hash: the app may have crashed after Codex accepted changed preferences but before provider state was saved. Synchronize current instructions on the next explicit submission; do not resubmit the interrupted question automatically. A later successful turn restores ordinary hash-based deduplication.
