# Application controller

- Keep operation transitions and shared documents under the controller mutex; release it before I/O or provider work. Deep-copy documents transferred to workers.
- Model discovery is independent of chat operation ownership. Register discovery in the worker lifecycle under the same mutex used by Close, and use the controller context so shutdown cancels it. Discovery must not change active chat, drafts, queue or configuration.
- Preserve the persistence/recovery and live-draft contracts in the parent guide. Run the controller tests under the race detector after changing concurrency or lifecycle behavior.
- Use the phase/kind constants in `types.go` and `chat.Status*`/`chat.Role*`; the frontend validates these values with Zod enums.
- Streaming previews live in `stream.go`, outside chat documents and the archive. Each Generate gets a sink bound to operation, attempt and block; closeStream on its result (and on the approach when the solution succeeds) drops later updates. `solveo:stream` carries the full preview set, coalesced to 100 ms; `StreamSnapshot` serves renderer reloads. Status changes only from Generate results. Login state (`LoginView`) is owned by the controller and published in `Snapshot`; the adapter may report completion before `StartLogin` returns, so an early result is held until the pending view exists.
- Work persistence is in `work.go`: persisters stay paused until New has initialized the active chat and history; recovery can mark them dirty but cannot start a writer or publish early. One `persister` per file writes the current in-memory state (never a queued older copy), coalesced 300 ms for drafts and 1 s for answer checkpoints; never call `flush` while holding `c.mu`. Queue changes are flushed synchronously after a capture and before PNG removal, so a restart cannot resurrect a removed image; a capture's operation ends only after its entry is written. Write failures surface as `Snapshot.WorkError` and are retried; an unreadable or newer `state.json` is never overwritten.
- `submitted{message_id, revision}` is flushed before archiving the question or calling the provider, including fast replies; a failed flush retains the unsent question in recovery. It marks the draft acknowledged by a running submit; after a crash the draft is cleared only if it still has that revision and the archive holds the message. DeleteChat writes the work state without the chat before deleting it from the archive; work of a chat missing from the archive moves to a new chat on start.
- Answer checkpoints outlive `closeStream` until `finishSave` (or the next submit) and become `Snapshot.Recovered` after a restart only for still-interrupted attempts. They are display-only: never archived, never in `llm.Request`; a retry of the message drops them. Crash tests: `work_test.go` (`crash` stops persisters, `reopen` starts a new controller on the same data).
- CLI log output goes only to the native log window (`NativeHost.SetLog`). Do not add it to `Snapshot` or publish snapshots per log chunk.
- Resolve images of the active/just-saved chat with `Archive.AttachmentPath` from in-memory metadata; `ImagePath` re-reads the whole chat document and is only for chats not in memory.
- Error texts returned to the UI are Russian; the UI shows them verbatim.
- Parallel answers remain one serialized controller operation with two child Generate calls. Only runParallel writes its document/archive; drain both results before idle or save-pending. Checkpoint early results, cancel/drain on storage failure, retain main continuation state and never let approach state replace it.
- Parallel retry uses the user turn's frozen RequestConfig and starts only solution; approach keeps its earlier attempt/status. Main success cancels an unfinished approach and ignores its late text. Main status governs cleanup, draft acknowledgement and user-turn status.
- Standalone approach receives bounded recent text excluding earlier approaches; text-only follow-ups receive the latest prior image set. No new provider call or retry occurs on renderer reconnect/RetrySave.

- Queue probes that fail with access/I/O errors protect the existing work state from rewriting and pruning until access is restored and the app restarts. SetDraft rejects edits after closing starts, so no accepted edit can arrive after the final snapshot. A normal Close that fails a final work write must return an error, restore a usable controller context and leave persisters running for retry.

- All local chat creation uses `newChat(instructions)` with a settings snapshot: startup, NewChat, DiscardUnsaved and restoreWork for missing chats. Capture settings under c.mu during runtime; startup restoration is single-threaded. Pass the chat snapshot to both llm requests; never inspect provider instruction hashes.
- `preparation.go` schedules optional ChatPreparer work only for the active empty chat without provider state. Register workers and snapshot config/global instructions under c.mu; no provider I/O under that mutex. Config/navigation cancels the old context before I/O and schedules the settled snapshot; global settings do not mutate the existing chat snapshot. Startup and DiscardUnsaved use the same path. Shutdown cancels/drains workers; aborted Close restores preparation on the new controller context. Submission preserves the preparation for atomic provider consumption, and passes the local ChatID to both request paths. Preparation never saves provider state or adds history messages.
- Successful matching login completion and a completed connection check reschedule empty-chat preparation; a startup account=null must not disable preparation until navigation. Preparation remains an optional capability and must not block or mutate UI/history.
